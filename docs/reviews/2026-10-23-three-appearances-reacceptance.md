## 剩余问题

### [P2] 对比度仍只在变化最强的区域取样，不能证明最弱落点达标

位置：`scripts/contrast-appearances.mjs:487`、`:524`、`:691`。

新实现确实用 CSS 字色与像素背景合成计算，而不是直接把抗锯齿字缘颜色当作字色；但它仍然保留：

```js
const cut = maxDiff * 0.9
// ...
if (maxDiff > 0 && diffs[p] >= cut) {
  // 只有入选位置才参与 weakestRatio
}
```

这会优先保留前景/背景差异最大的区域，恰好排除需要找出的低对比度区域。换计算公式并没有消除该筛选偏差。

**独立反例已实际执行，直接调用当前文件原样提取的 analyzePair：**

1. 500×70 的画布，左半白底，右半 `#333333` 底。
2. 两侧均绘制纯黑、24px 加粗文字，生成正常图和去文字底图。
3. 对黑字与右侧深灰底，真实对比度为 **1.6621:1**，低于正文 4.5:1 和大字 3:1。
4. 当前函数返回 **weakestRatio = 21**，最终判 **通过**；weakestPoint 位于左侧白底。

复现脚本：`tmp/recheck-probes.mjs`。证据：`screenshots/appearance-recheck/probes.json`、`contrast-counterexample.png`。

这是测量工具的确定性漏报；**不据此断言现有产品页面存在 1.66:1 的文字**。但报告中的“454 项全部通过、最低 4.61:1”仍不足以证明最弱落点满足要求。

修复要求：

- 将文字位置识别与原背景对比度解耦。例如逐文本片段在受控底色上生成字形掩膜，再回到原底图逐落点计算；多色后代应按各自实际字色配对。
- 不用“原始两图全局最大差值的 90%”定义最终判定的采样位置；单纯改成差值大于零也需防止动画、边框、图标污染。
- 加入此反例和单色合格文本的算法回归：反例必须低于阈值且进入失败列表，合格文本保持通过。
- 重跑正式目标，更新交付报告。可将抗锯齿像素比值继续作为参考量，不作为字体对比度门禁。

### [P3] 真实缩放成立，但最小档实际未达到标称 195px

位置：`scripts/zoom-real-200.mjs:753`、`:849`、`:862`。

已检查交付的 `screenshots/zoom-real-200/zoom-real-200.json` 原始数据：100%→200% 时 dpr 1.25→2.5、innerWidth 1426→713、outerWidth 1440 不变、visualViewport.scale 保持 1。这组证据可以接受为真实浏览器页面缩放。本轮没有重新执行桌面键盘注入，结论限于已交付证据审查。

但是 `half-390-window` 的 9 个组合均是：

| 指标 | 值 |
|---|---|
| requestedCssWidth | 195 |
| actualCssWidth | 243 |
| actualInnerWidth | 251 |
| devicePixelRatio | 2.5 |

浏览器窗口存在最小宽度等限制时，设置外窗宽度不等于实际获得目标 CSS 宽度。当前脚本无目标偏差校验，仍把这 9 组计入 195px 档的完整覆盖。其它档位也有边框/滚动条导致的差值，但本项是显著偏差。

修复要求：记录并核对实际宽度，未达到的档位标记未覆盖或明确平台限制；如果采用实测 243px，就更正档位名称和覆盖说明。**不要求项目支持 195px，也不要求把低于 320px 的布局溢出改为产品失败。**
